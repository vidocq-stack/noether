= Noether
:description: Jakarta Persistence 3.2 provider for Java 25: entity access generated at build time, strict Java Modules, JDBC on the calling thread.

[.lead]
Noether is a Jakarta Persistence 3.2 provider. It maps entities, keeps the persistence context, translates JPQL and
Criteria to SQL and runs it over JDBC, like Hibernate ORM or EclipseLink. What it does differently is how it reaches
your entities: the annotation processor writes their access at compile time, so nothing reflects into your classes
and no bytecode is woven into them, at build time or at run time.

== Origin of the name

Emmy Noether (1882–1935), the German mathematician whose work reshaped abstract algebra and whose theorem ties every
symmetry of a physical system to a quantity it conserves. See
https://en.wikipedia.org/wiki/Emmy_Noether[the Wikipedia article].

A persistence provider lives on that kind of invariant: what an application changes in memory and what the
database holds must stay the same thing across every flush, every transaction and every restart.

== Three identifying traits

. **No reflection on entities.** `noether-jpa-processor` reads your entities at compile time and writes, next to
  each of them, the class that instantiates it and reads and writes its state. Noether calls that class. An entity
  compiled without the processor gets the same class generated with the JDK's Class-File API when the factory
  starts. No ASM, no Byte Buddy, no bytecode enhancement of your classes, no dynamic proxy.
. **Strict Java Modules.** Every Noether artifact is a named module. On the module path, the generated access is
  handed over through `ServiceLoader`, so your entity packages stay closed: no `opens`, no `exports`, no
  `--add-opens` at launch.
. **JDBC on the calling thread.** A query, a flush or a lazy load runs on the thread that asked for it, and nothing
  holds a monitor across a blocking call. Code on a virtual thread stays on its virtual thread.

Noether was extracted from Mansart on 2026-10-11. Mansart keeps Jakarta Data, the connection pool and Jakarta
Transactions. The two serve different needs:

* **Jakarta Data** (`mansart-jakarta-data`): typed repositories declared as interfaces, stateless, with no
  persistence context. Enough for most CRUD services. See xref:mansart::modules/mansart-jakarta-data.adoc[Mansart
  Jakarta Data].
* **Jakarta Persistence** (Noether): the `EntityManager`, a persistence context that tracks managed entities and
  writes their changes at flush, relationships loaded on demand, lifecycle callbacks, JPQL, Criteria and entity
  graphs. For domain models with rich relationships, and for applications ported from Hibernate ORM or EclipseLink.
