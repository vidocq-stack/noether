= Internals
:description: Static generation, Java Modules and provider discovery.

Entity metadata is read from class files. `AccessPlanner` is shared by bootstrap
and the annotation processor; generated access handles state without reflective
field/method invocation. The JDK Class-File API is used, not ASM or Byte Buddy.

For eligible lazy to-one targets the same planner feeds `LazySubclassGenerator`.
APT writes the subclass class file and the generated access's `instantiateLazy` factory
inside the application's module. The existing access provider supplies it through
ServiceLoader: a closed package needs neither exports nor opens, and no bytecode is
generated at runtime on this path. Opaque precompiled entities instead use bootstrap
generation, requiring their existing package opens to `io.vidocq.noether.jpa.core`.
Their module must also read that provider module for the reference SPI; an opened module
without that read edge stays eager, with no read edge injected by the provider.
The planned JPA Maven-plugin module is not delivered; there is no separate plugin
generation path. No runtime reflection or instrumentation is introduced.

Each pending reference is already the managed object for its identity, not a placeholder
replaced later by `find`. The first intercepted call hydrates it in place, records its
snapshot and invokes `PostLoad`. The identifier getter stays callable without SQL when
it only reads the identifier; all other accessible declared methods, including setters,
initialize first. Final/native/abstract methods, exposed instance fields, interfaces and
inheritance are conservatively excluded.
Every `EntityLoader` read runs in a load scope of the persistence context: `PostLoad`
is queued and invoked when the outermost load returns, once the collections initialized
inside it are complete in place (BUG-20261016-01). Each freshly loaded entity still gets
one callback before `find`, `refresh` or the query returns. XML fetch/column overlays share the normal model,
but identifier/access-plan changes fall back to eager loading.

Unloaded reference entries are excluded from flush and persist cascades, and detached
unloaded state is ignored by merge. Shared-cache graphs containing unloaded references
are not captured, avoiding a forced load or retained context. An eager cache graph that
would reuse an existing unloaded reference falls back to ordinary loading before allocating
any nodes, preserving identity and eager semantics. Fully loaded graphs retain the original
cache behavior. Collection graph nodes keep secondary selects; eligible query graph to-ones
reuse the D11 path (D14 below), and eligible collection fetch joins use the D12 path below.

Eligible to-one fetch joins (decision D11) add the target's statement columns — primary and
secondary tables — to the translated select (`Compiled.hydrations()`, fetched entities first).
After reading each row, the query hands them to `EntityLoader`, which builds the entity as
`find` does: generated access, converters, relationships, snapshot, `PostLoad` and shared-cache
storage. A known identity is never overwritten; an unloaded reference of that type is hydrated
in place. A row whose target key columns are all null hydrates nothing.

For one eligible collection fetch (D12), the same statement-column pipeline captures every
owner and entity target, plus element values, row presence and stored list/map indexes.
`EntityLoader.loadCollection` registers all identities before relationship resolution,
then resolves staged relationships before collection assembly (sorted target comparators
can read those relationships). It reuses the collection assembler and generated access,
completes unloaded wrappers in
place, retains dirty managed state, then records whole snapshots and invokes callbacks.
Shared-cache publication follows complete assembly, never a partially accumulated collection.
Non-`DISTINCT` queries retain repeated owner references; `DISTINCT` removes repeated managed
identities without discarding equal bag elements or merging different owners with equal
application `equals` implementations.

Eligibility is one root entity selection and exactly one declared collection fetch, without
grouping or locking, concrete owner/target statement mappings, basic/embeddable values,
stored list positions, basic map keys or derived `@MapKey`. Multiple/nested/embedded fetches,
extra joins, restricted collection aliases, polymorphism, entity/embeddable map keys and
complex query shapes keep complete secondary loading. Eager relationships outside the
fetched collection may require additional statements. D13 fixes the common assembler's
null-element omission (BUG-20261015-09): real element rows retain null values, while an
absent LEFT row is filtered by its separate owner-FK presence marker.

Explicit pagination takes a separate safe path: a single-root entity selection with no
grouping/lock and scalar root ordering pages *distinct owner identities in SQL*, then runs
the ordinary complete collection fetch plan. Sort columns are projected for PostgreSQL's
distinct-ordering rule but are not user result items. Other pagination shapes throw
`PersistenceException` before SQL: never a joined-row limit or hidden in-memory pagination.
Unbounded single-result calls read every collection row.
The pagination check uses the translator's actual collection-join metadata, including
entity-join aliases and set operands, rather than a second mapping/path interpreter.

== Query graph SQL loading (D14, 2026-10-15)

At each execution, `JpqlQuery` snapshots the current graph hint and
`Translator.graphSelect` lowers eligible direct/nested to-ones to LEFT fetch joins.
No graph plan is cached across mutable graph or hint changes. Unconditional explicit
fetch joins are reused; query predicates, parameters, ordering and pagination stay intact.
The existing D11 statement-column hydration handles null targets, identity, dirty state,
in-place lazy references, converters, secondary tables, snapshots, callbacks and cache.

Eligibility is one concrete-root entity selection, no distinct/grouping/locking/set query,
explicit collection fetch or conditional/treated join. D11-unsupported target types,
embedded/treated nodes and collection nodes outside D16 retain complete follow-up loading.
FETCH contributes explicit nodes; LOAD additionally expands mapped eager to-ones,
guarded against eager type cycles. The ordinary loader may overfetch FETCH's omitted
eager state, as permitted by the specification: no eager requirement is suppressed.
Nested/multiple collection SQL fetching remains a separate future lot.

== Find graph SQL loading (D15, 2026-10-16)

`EntityManagerImpl.find` keeps managed-instance and shared-cache checks before SQL.
Eligible non-locking database reads use `Translator.graphFind`, which shares D14's
`graphSelect` planner and adds predicates using the translated root key expressions
and existing key binders, including normalized composite identifiers. Discriminator
restrictions are preserved. `JpqlQuery.findGraph` shares the fetched-column reader but
does not execute an EntityManager query or invoke query auto-flush. The existing staged
loader registers identities before relationships, snapshots and callbacks; unloaded
root/target references hydrate in place and known dirty state is preserved.

The 3.2 typed graph overload uses the same route. Graphs are validated and reread per
call; find retains its existing merged plan when both hints are supplied. LOAD eager
expansion and FETCH overfetch rules are unchanged. Initialized managed roots and L2
hits retain normal graph completion without an unnecessary root query. Cache policy,
generation fences, lock/timeout/refresh behavior and connection ownership stay in find.
Plain/locked finds, unsupported D11 root/target types and graph paths keep ordinary
loading; collection nodes outside D16 initialize fully through follow-up statements.

== One collection graph SQL loading (D16, 2026-10-16)

`Translator.graphSelect` recognizes one root leaf collection with no existing joins.
Before adding a LEFT fetch join it compiles the candidate against D12's collection
collector, so unsupported map/target/query shapes do not gain multiplying joins.
DISTINCT is admitted on this collection path only. Subgraphs, multiple collections
and explicit to-one graph nodes keep the existing planner/follow-up behavior.

`JpqlQuery` uses the execution-time plan to decide whether SQL row limits are safe;
collection pages reuse SQL distinct-owner pagination and complete secondary loading.
Synthetic collection graph rows are deduplicated by managed identity, unlike ordinary
non-DISTINCT explicit fetch-join results. No query predicate becomes a graph filter.

`Translator.graphFind` retains collection metadata and existing key predicates.
`JpqlQuery.findGraph` shares the query's collection-row decoder and D12 staged loader,
not query execution or auto-flush. The existing assembler retains empty/null distinction,
duplicates/order/keys, in-place wrappers/references and dirty state, and completes state
before snapshots/callbacks/cache. No new SQL AST, loader, runtime reflection, dependency,
module, package or executor is introduced. D13 batching and D14/D15 to-one SQL are unchanged.

== Collection to-one subgraph SQL loading (D17, 2026-10-16)

When the single graph collection is entity-valued and its element subgraph contains only
basic/embedded leaves and to-one chains to concrete D11-hydratable targets,
`Translator.graphSelect` also plans those to-ones (and, under LOAD, the elements' eager
to-ones) as LEFT fetch joins from the collection alias, reusing D14's planner. The whole
statement is compiled against the D12 collector before use; on failure it retries the plain
D16 collection join, then the original statement. Any collection node inside the subgraph,
polymorphic/non-hydratable target, unknown attribute or embedded subgraph rejects the
collection path and keeps D14/D15 behavior.

For synthetic graph rows only, `Translator.collectionHydration` accepts extra joins: each
must be an unconditional LEFT fetch of a single-valued association from the collection or
an already chained alias, without `ON`, `TREAT` or restrictions. Their entity hydrations are
added after the owner and element, so one row hydrates owner, element and targets through
the existing staged loader. Explicit fetch-join statements keep the D12 one-join rule.
`JpqlQuery` passes the graph-row flag to the translator and pages owners from the original
statement, then lets the ordinary graph follow-up complete collections and subgraphs.

== Mixed root and element graph branches (D18, 2026-10-16)

`Translator.graphCollection` now admits root to-one branches beside the one collection,
validating each through the existing to-one-subgraph eligibility check. It still rejects
a second collection or collections nested on either branch. `graphSelect` invokes
`graphJoins` for both element and root branches with *one shared alias sequence*, avoiding
collisions between branches and with user aliases. Existing finite explicit graph
recursion and automatic eager-cycle guards remain; LOAD expands both branches.

For synthetic graph rows only, `collectionHydration` accepts validated LEFT to-one
chains starting at the owner *or* element alias. Owner and entity element stay the first
two hydrations, followed by all branch targets; basic/embeddable collection payloads
retain their own readers. This reuses `JpqlQuery`, the dialect AST and `EntityLoader`
unchanged: row identities are registered before relationships, collections are assembled
without a to-one Cartesian multiplier, and snapshots/callbacks/cache see the complete
graph. Existing dirty instances and lazy wrappers/references retain their identity.

The combined graph is validated against the same collector before use. Unsupported
shapes retain complete established fallback; explicit fetch joins are unchanged.
Pagination still pages SQL distinct owners from the original statement and completes
the graph through secondary reads. Managed/cache find hits retain ordinary completion
and find gains no auto-flush. There is no second planner, raw SQL, runtime entity
reflection, new dependency, package, module or executor.

== Split root collection collectors (D19, 2026-10-16)

`Translator.splitGraph` validates each requested root collection using the existing
single-collection planner/collector. The user query still selects only owner identities
(including SQL distinct-owner pagination), and each synthetic collector receives
bounded owner-key predicates through the dialect AST. D13's configured owner bound
and 512-parameter ceiling are reused. Each statement has one collection join, plus
the existing LEFT root/element to-one branches and cycle-guarded eager expansion.

`JpqlQuery` captures all independent branch rows before hydration.
`EntityLoader.loadCollections` registers all identities through `loadRows`, skips
all collected attributes while resolving relationships, and assembles every complete
collection with the existing assembler before taking snapshots or queuing callbacks.
The BUG-20261016-01 scope also covers outer query/find graph completion, so callbacks
cannot expose an unfinished sibling branch. Existing wrapper/reference completion,
dirty state and cache-generation publication are retained.

This extends D18, not a second mapping/hydration architecture. Unsupported nested
collections, non-root eager collections, polymorphic/complex mappings and broader
query shapes retain complete fallback. Explicit fetch joins and single-collection
graphs retain their existing collectors.

== Two collection stages (D20, 2026-10-16)

The shared split planner now returns at most two collector stages. First-stage
templates retain root and element to-one LEFT joins but cut second-level collection
nodes into plans merged by mapped owner type and collection. This also handles
second collection owners reached through element to-ones. Second-stage templates
pass the same single-collection checks; a third collection edge rejects the split
plan and retains ordinary complete loading. Eager to-one expansion is path-cycle
guarded; unsupported eager collection closures retain fallback.

Execution captures the full first-stage rows, deduplicates nested owner identities,
then reads each second-stage collection with that owner's key-width batch bound.
No nested read is issued for an empty owner set. Only after both stages have been
captured does the unchanged multi-collection loader register identities and resolve
relationships, complete wrappers, snapshot and queue callbacks. Managed/cache
completion uses the same planner even if only nested collections remain unloaded.
Fully complete graph hits need no SELECT or new JDBC connection; the completeness
check runs before connection acquisition (BUG-20261016-03). Find does not auto-flush.

BUG-20261016-02 was exposed by the nested managed-bag gate: deleting one occurrence
with an owner/target predicate deletes all duplicate join rows. Duplicate-bearing
snapshots now reuse whole-owner rewriting; unique unindexed bags retain diff writes.
No new mapping representation, SQL renderer, dependency or entity access mechanism
is introduced. D19 above remains the historical root-collection delivery.

== Root to-one collection stages (D21, 2026-10-16)

The split planner first prunes requested collection edges from finite root to-one
paths. A collection-free seed reuses the D14–D18 LEFT joins and generated-access
hydration. SQL-selected root IDs constrain each seed batch. The seed's intermediate
owner identities then feed the same D19/D20 single-collection templates, at no
more than two collection depths. Requests are grouped by mapped owner type and
attribute; compatible owner-type requests occurring at both depths move to the
later stage, after all preceding rows have contributed their distinct identities.

Each template uses its owner's key width and existing 512-parameter bound.
Absent to-ones contribute no owner ID. Seed rows and both collection stages
are captured before the unchanged multi-collection loader completes identities,
relationships, wrappers, snapshots, cache and lifecycle callbacks. Collection-free
seed templates use the same dialect AST/key binder path as collection templates.
No new SQL renderer, reflection, proxy, dependency, module or thread facility is
introduced. Find keeps no-auto-flush and complete managed/cache JDBC-free hits.

An explicit cyclic/type-revisiting path, third collection edge or unsupported
eager/mapping closure rejects this new split plan before SQL execution and leaves
complete fallback/refusal to the established loader. Automatic eager expansion
is still cycle guarded. D14–D20's earlier eligible paths and explicit fetch joins
are unchanged; the preceding sections remain their historical records.

== Three nested collection stages (D33, 2026-10-18)

D33 extends the root-collection split route to at most three collection edges on
one nested graph path. The planner separates nested collection requests into
owner stages while retaining eligible to-one branches in each collector. A
stage's distinct entity identities constrain the next stage, and each collector
uses that owner's existing key-width and 512-parameter batch bound.

The query still selects/pages root identities before the complete collection
stages; non-locking finds start from the requested root identity. All stage rows
are captured before the existing loader registers entities, resolves links,
completes wrappers, snapshots, publishes cache entries or dispatches callbacks.
No new loader or SQL join is introduced.

This extension applies to nested collection paths beginning at a root
collection. At D33, D21's separate root-to-one seed path still had its original
two-edge limit; D34 extends that route to three edges too. Type-revisiting
explicit cycles, a fourth edge, unsupported eager closures and non-hydratable or
complex mappings reject split execution before SQL and retain the complete
established fallback/refusal.

== Three collection stages through root to-one paths (D34, 2026-10-18)

D34 expands the root-to-one route's owner-stage plan to three collection levels.
Compatible requests for the same mapped owner type are merged into the latest
stage, whose input includes identities captured by earlier stages; this keeps
one grouped collection read after the available distinct owners have been
discovered. The existing `splitRows` pipeline collects every stage before
relationship registration and callbacks. Root-only SQL pagination and each
collector's parameter bound are unchanged.

The fourth collection edge, type-revisiting explicit paths, unsupported eager
closures and unsupported query/mapping shapes still select complete fallback
or refusal before split SQL runs.

== Lazy read batches (D13, 2026-10-15)

`EntityLoader` groups pending compatible persistence-context entries on first access.
The requested identity is always included before other entries; initialized state,
removed/detached entries and unloaded collection-owner references are not inspected or
overwritten. Simple keys use dialect-AST `IN`; composite owners use ORs of whole tuples.
The factory setting defaults to 16, permits 1–256 (1 disables) and each statement has
at most 512 key parameters. No new mapping engine, raw SQL or runtime dependency is used.

Collection reads select owner keys plus existing mapped element/index columns and
distribute them to complete groups, including empty owners and persisted null basic
elements. Entity-valued elements then use bounded full statement-column reads through
the D12 staged registration/hydration path; there is no `find` loop. Known dirty managed
targets are retained, and existing references hydrate in place. Wrapper identity and
snapshot baselines are preserved. Replaced snapshot wrappers use the ordinary loader,
which is needed by flush/orphan removal without replacing the new collection.

To-one groups use the same full-state read/hydration path and existing generated
subclasses. Duplicate referenced identifiers share one managed object. A missing requested
target throws `EntityNotFoundException`; missing incidental references remain unloaded.
No row-count limit can truncate a collection. Each owner group is bounded; large entity
collections can require multiple bounded target groups.

Eligibility is intentionally conservative: single-table/non-polymorphic owners/targets,
element collections, owning join-table/target-FK collections and inverse target-FK
collections; non-entity map keys. Secondary tables, inheritance, inverse join tables and
entity map keys retain the complete ordinary loader. D10 reference eligibility and
EAGER/fetch/graph contracts are unchanged. Batches run on the existing transaction/read
connection, with no auto-flush, per-identity L2 lookup or forced publication. Normal
cache publication and unloaded-reference exclusions remain; detach/clear/close still
disconnect pending state. SQL-count regressions are correctness tests, not benchmarks.

Java module descriptors expose minimal public contracts and qualified
processor access. Dialects, generated entity accesses, CDI extensions and
Persistence/Validation providers are registered through the appropriate
`provides`/`uses` contracts; service resource files retain classpath discovery
for the standalone official TCK harness.

JDBC execution uses virtual threads. The external Mansart transaction identity
is captured before virtual-thread offload. The extraction does not change
transaction or pool behavior.
