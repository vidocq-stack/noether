= Reference
:description: Noether artifacts and external integrations.

All Noether artifacts are under `io.vidocq.noether`:

[cols="2,3"]
|===
| Artifact | Role
| `noether-root` | Repository reactor
| `noether-jpa` | Persistence aggregator (directory `noether-persistence`)
| `noether-jpa-core` | Persistence provider
| `noether-jpa-dialect-spi` | SQL AST and dialect contract
| `noether-jpa-dialect-h2`, `noether-jpa-dialect-postgresql` | Dialect adapters
| `noether-jpa-processor` | APT and generated entity access
| `noether-jpa-cdi` | Vauban CDI and Mansart JTA bridge
| `noether-validation`, `noether-validation-core` | Provisional local-only Validation
|===

Java module names retain their suffixes under `io.vidocq.noether.jpa.*` and
`io.vidocq.noether.validation.*`. External dependencies stay under
`io.vidocq.mansart` and `io.vidocq.vauban`. `mansart.version` pins the independent
Mansart version. Integration vehicles and all provisional Validation artifacts
are excluded from release publishing.

== Query entity graph hints

[cols="2,4"]
|===
| Standard hint | Query SQL contract (D14)
| `jakarta.persistence.fetchgraph`
| Explicit eligible to-one nodes/subgraphs become LEFT fetch joins. Omitted eager
attributes may still be overfetched by the loader; they are not guaranteed unloaded.
| `jakarta.persistence.loadgraph`
| The same explicit nodes, plus eligible mapped eager to-ones (cycle-guarded expansion).
|===

If both hints are present, FETCH retains its existing precedence. Graph objects must
belong to the same persistence unit and match the query root under the existing
validation rules. Graph/hint changes are reread per execution.

SQL scope: one concrete-root entity selection, no distinct/grouping/locking/set query,
explicit collection fetch or conditional/treated joins. Unsupported target types,
embedded/treated graph nodes and collection nodes outside D16 below use complete existing follow-up
loading. Mixed graphs may combine same-row to-ones with complete collection reads.
No eager requirement is suppressed; D10 lazy eligibility and D13
batch bounds remain unchanged. See xref:internals.adoc[] for the shared hydration path.

== Find entity graph hints (D15, 2026-10-16)

The same standard hints drive eligible direct/nested to-one SQL for non-locking
database finds. Composite root keys, mapped converters and secondary-table columns
use existing binders/hydration. The 3.2 `find(EntityGraph, id, options)` overload is
equivalent to FETCH. Unlike queries, find retains its existing merged plan when both
validated graph hints are supplied. Mutable graph nodes are reread per invocation.
LOAD includes eligible eager to-ones; FETCH may overfetch omitted eager state.

Managed-instance and L2 cache hits retain their fast paths and graph initialization;
unloaded references hydrate in place, dirty state is not overwritten and find never
auto-flushes. Existing retrieve/store/BYPASS/REFRESH, lock/timeout and refresh semantics
are unchanged. Plain/locking finds, unsupported polymorphic/inherited types and
unsupported graph paths retain ordinary loading. Collection nodes outside D16 below
use complete follow-up loading.

== One leaf collection graph (D16, 2026-10-16)

Both graph hints can join one explicitly requested root collection through the
existing collection-fetch assembler. Eligible queries select one concrete root,
optionally DISTINCT, with no existing joins, grouping/having, set operations or locks.
Eligible non-locking database finds use the same path, including unloaded managed roots.
Basic graph attribute nodes may coexist, but explicit to-one association nodes and
(at D16 delivery) all subgraphs retain D14/D15's existing loading instead; D17 below
adds to-one subgraphs on the collection.

The join is LEFT: empty owners remain and null element rows remain distinguishable
from absence. Synthetic graph joins do not duplicate query roots. Entity, basic and
embeddable collections retain duplicate bags, list positions/order, sorted sets and
supported basic/derived map keys. Collections complete before snapshots/callbacks/cache;
managed dirty state and wrapper/target identity are preserved. Other mapped eager state
remains loader work, including LOAD requirements and permitted FETCH overfetch.

Finite owner pagination pages distinct owners in SQL, then loads their whole collections
through secondary reads. Unsupported collection paging throws before SQL; no silent
in-memory pagination or partial collection. Explicit JOIN FETCH semantics are unchanged.
Managed/cache find hits keep their fast paths; find does not acquire query auto-flush.
Mutable graphs and replacement hints are reread on every execution.

Multiple collections, nested-to-one collection subgraphs, mixed to-one nodes,
extra/filtering joins, complex/polymorphic/inherited shapes, embedded/treated paths,
and entity/embeddable map keys keep complete existing fallbacks. Nested/multiple
collection SQL is future work, not a Cartesian-product expansion.

== One collection with to-one subgraphs (D17, 2026-10-16)

The single graph-requested root collection of D16 may carry an element subgraph, when the
collection is entity-valued and the subgraph holds only direct or nested to-one nodes
(for example `lines { product { supplier, category } }`) to concrete, non-polymorphic
entities, plus basic/embedded leaves. Every to-one becomes a LEFT fetch join from the
collection alias, and owner, element and targets are hydrated from the same rows. LOAD
also joins the elements' mapped eager to-ones; FETCH may overfetch omitted eager state.
The same query/find shapes as D16 apply.

Null targets never filter elements; empty owners, null elements, bag duplicates, list
positions and basic/derived map keys are preserved; shared targets keep one managed
instance. Dirty managed entities and collections are not overwritten, unloaded lazy
references complete in place, and `PostLoad` runs once per fresh entity after the
whole graph is assembled; callback mutations remain dirty and failures propagate.
Finite owner pagination pages distinct owners in SQL without the graph joins, then loads
collections and subgraphs through complete secondary reads.

Multiple collections, collection-valued nodes inside the subgraph (including element
collections of targets), polymorphic/inherited targets, embedded subgraphs, root to-one
nodes beside the collection and the D16 query/map-key restrictions keep the complete
existing fallback. Explicit JOIN FETCH semantics are unchanged.

== Mixed root collection and root to-one graphs (D18, 2026-10-16)

D18 extends the historical D16/D17 scopes above: exactly one explicitly requested
root collection may coexist with direct/nested root to-one branches, for example
`Order { customer { favorite { supplier } }, lines { product { supplier } } }`.
The collection may hold entities (with D17 element to-one subgraphs) or D16
basic/embeddable values. Root and element targets must be concrete D11-hydratable
entities; all explicit subgraphs contain only to-ones and basic/embedded leaves.
Both branches use LEFT joins in one SQL statement for eligible JPQL/Criteria and
non-locking database finds. LOAD also joins mapped eager to-ones on both branches;
FETCH may overfetch eager state.

Null root/element targets never filter owners or elements; empty owners, null
basic elements, duplicate bags, list positions/order and supported map keys survive.
Shared root/element targets have one managed identity, with dirty state, in-place
lazy references/wrappers and complete lifecycle/snapshot/cache behavior preserved.
Callbacks run once per fresh identity after assembly, and their mutations remain
dirty. Mutable graphs and replacement hints are planned at each execution.
Managed/cache find hits keep ordinary graph completion and never auto-flush.

The D16 query/mapping restrictions remain. Pagination uses SQL distinct-owner paging
without synthetic graph joins and then complete secondary graph loading, not
single-query or in-memory pagination. Multiple root collections, collections nested
under either branch, unsupported map keys, polymorphic/inherited/complex shapes and
explicit fetch joins retain their established complete fallback or explicit refusal.
Multiple collection SQL fetching, nested collections, broader fetch eligibility and
broader lazy/batch/mapping support remain separate prioritized roadmap items.

== Multiple root collection graphs (D19, 2026-10-16)

D19 supersedes only the historical multiple-root-collection fallback above. Two or
more requested root collections, for example `Order.lines.product` and
`Order.payments`, are read through *independent grouped SQL collectors*, never one
Cartesian collection join. Root/element to-one branches retain D18 LEFT hydration.
Mapped eager root collections become additional collectors; eager to-ones are joined
for LOAD and permitted FETCH overfetch.

Eligible JPQL/Criteria select one concrete root entity (DISTINCT allowed), without
explicit joins, grouping, locks or set operations. Each branch must pass the existing
D16–D18 mapping checks. Query SQL selects owner identities, then each collection is
read for groups bounded by `min(fetch.batch-size, floor(512 / owner-key-width))`.
The setting below defaults to 16 and accepts 1–256; 1 disables owner grouping.
For `C` collectors and `N` owners this is `1 + C * ceil(N / bound)` SELECTs;
eligible non-locking database finds need `C`. No per-element find is used.
SQL distinct-owner pagination (scalar root order only) precedes complete split reads.

All rows/identities/collections are staged before snapshots and callbacks. Empty
owners, null elements/targets, bag duplicates, indexed lists/maps, shared managed
identity, dirty state, in-place wrappers/references, cache and no find auto-flush
contracts are preserved. Complete managed/cache graph finds need no SELECT.
Plans are rebuilt for mutable graphs/hints.

Nested collection-valued subgraphs, non-root mapped eager collections, unsupported
polymorphic/complex/map-key shapes and broader query/locking shapes retain complete
loading/refusal. Omitted unsupported lazy mappings can retain D10's eager fallback;
dirty in-memory association changes also require ordinary completion. The SELECT
bound does not cover those extra fallback reads. Single-collection and explicit
JOIN FETCH SQL remain unchanged. Nested collection graphs, broader fetch/lazy/batch
eligibility and missing mappings are the remaining prioritized lots.

== Two collection graph edges (D20, 2026-10-16)

D20 supersedes D19's nested-collection fallback for *two collection edges beginning
at a root collection*: `Order.lines.discounts`, or `Order.lines.product.tags`.
Multiple independent root and second-level branches are supported; finite root,
element and leaf to-one chains retain LEFT hydration. Second-level entity collections
and existing eligible element-collection leaves use the same collectors/assembler,
preserving null rows, bag multiplicities, stored positions and supported map keys.

Queries select and paginate root identities in SQL, then read first-level collections
and grouped second-level collections separately. Shared nested identities are
deduplicated, and requests for the same mapped owner type/collection are merged.
For each collector `c`, let `Nc` be its distinct owner count and
`Bc = min(fetch.batch-size, floor(512 / owner-key-width))`.
An eligible query uses `1 + sum(ceil(Nc / Bc))` SELECTs; a non-locking database find
omits the initial root selection. The configured default/range remain 16 and 1–256;
1 disables grouping. Composite nested owners use their own key width, not the root's.
Empty nested owner sets cause no SELECT. All stages precede relationships, complete
assembly, snapshots, cache publication and callbacks. Dirty state and in-place lazy
wrappers/references survive; complete managed/cache finds need no SELECT, new JDBC
connection or auto-flush.

This is bounded graph loading, not arbitrary-depth fetching. Third collection edges,
collections under root to-one branches, unsupported eager closures, polymorphic or
otherwise non-hydratable targets, entity/embeddable map keys, embedded graph subpaths,
explicit joins/grouped/having/multi-root/multi-selection/set/locking queries and locking
finds retain complete ordinary loading or established explicit refusal. Existing
owner-pagination guards still apply; no collection-row limit or in-memory pagination
is introduced. Counts exclude ordinary completion for dirty in-memory association
changes and omitted unsupported lazy mappings. Explicit fetch joins and unnested
single-collection graphs keep their existing collectors. Deeper graphs and broader
fetch/lazy/batch/mapping eligibility remain separate backlog items.

== To-one relationships in element-collection values (D24, 2026-10-16)

Embeddable `@ElementCollection` values support owning `@ManyToOne` and
`@OneToOne` to non-polymorphic, single-table targets with supported direct
primary keys. Simple IDs and composite IDs represented by `@EmbeddedId` or
`@IdClass` are supported when every key component is BASIC. Annotation and
metadata-complete ORM XML share the existing builder, binders and generated
accesses, including nested/record values and map association overrides named
`value.target`.

The collection-table row owns the target FK. The target's ID type is retained,
nullability/optionality is honored and one-to-one FK columns are unique.
Schema generation creates target tables before adding these FKs. Owner key,
list position and stored map key are separate columns.
The new verified map contract uses stored basic keys; entity/embeddable-key
mapping support is not extended by this lot.

Embeddables have no entity identity. A changed collection is deleted by its
owner's complete key and rewritten with all occurrences and positions/keys.
No selective deletion matches a bag row by embeddable equality; equal duplicate
values, repeated targets and null rows are retained. Collection changes version
the owner, whereas edits solely to target state do not.

The collection remains LAZY/EAGER as mapped; once initialized, its references
resolve eagerly to actual managed target identities. Persist/flush cascades
including generated target IDs, merge copying/identity resolution, refresh,
detach/remove cascades and shared-cache restoration use the existing lifecycle
machinery. Removing a collection value is not orphan removal.

Tested query support covers JPQL/Criteria basic collection-join attributes and
JPQL `KEY`/`INDEX`. D27 adds bounded association navigation and to-one entity
projections; D28 adds whole relationship-bearing value projections. Collection
fetch joins and fetch graphs use complete ordinary loading; owners with these
values are not eligible for optimized row hydration or lazy batching.

== Composite primary-key targets (D29, 2026-10-17)

Owning element-value to-ones may target direct composite primary keys represented
by `@EmbeddedId` or `@IdClass` when every key component is BASIC. Explicit
`@JoinColumns` resolve each referenced key component, including when declared in
an order different from the target identifier. The collection row stores the
complete key tuple; schema generation creates one composite FK and, for
`@OneToOne`, a grouped uniqueness constraint. Metadata-complete ORM XML has the
same behavior.

An all-null FK tuple means a null association. A partially null tuple is rejected
when read rather than treated as a valid composite identity. JPQL/Criteria
association navigation and whole-value projections resolve the target's managed
identity through the same tuple.

Composite keys containing non-BASIC components, derived composite keys,
business-key joins, inverse `mappedBy`, orphan removal, to-many/nested
collections, join-table relationships, read-only/shared/other-table FK columns,
polymorphic/JOINED/TABLE_PER_CLASS targets and unsupported owner keys/indexes
remain unsupported.
Broader query and mapping support requires separate bounded lots.

== Simple MapsId primary-key targets (D30, 2026-10-17)

An element-value owning to-one may target an entity whose simple `@Id` is a
shared primary key derived through one owning `@OneToOne @MapsId` to a
non-polymorphic parent with a simple `@Id`. The element-row FK references the
target's actual physical primary-key column, including when the parent join
column supplies that column name. Annotation and metadata-complete ORM XML use
the same mapping, schema, lifecycle and query paths; generated parent IDs are
available to the collection row after ordinary persist ordering.

Composite or nested derived identities, chained `@MapsId`, business-key,
polymorphic and other unsupported target mappings remain outside this support.
This does not widen collection fetching, graph hydration, lazy references or
batching.

== Inverse collection-element boundary (D25, 2026-10-17)

This is a bootstrap-validation follow-up, not inverse relationship loading.
Persistence 3.2 §2.7 gives embeddables no entity identity: an association back
from a referenced entity must target the containing entity, never an element.
§2.8 requires collection embeddables to own their many-to-one/one-to-one FKs.
`ManyToOne` has no `mappedBy`; the corresponding inverse is an entity
`OneToMany`. The standard dotted paths (§11.1.31, §11.1.42) describe single
embedded attributes, not element-collection traversal.

Annotation/XML associations targeting embeddables, and `mappedBy` paths crossing
an element collection (list, bag, map, or below another embedded attribute), fail
at bootstrap before schema generation. Ordinary single-embedded inverse paths
remain supported. A possible inverse toward containing entities needs a separately
proven contract and is unsupported, not declared universally illegal here.

A unique FK in collection rows does not establish one-to-one cardinality between
containing entities: one owner may reference several different targets through
different rows. Duplicate values/targets and list/map positions do not create
element identity. No inverse FK/column, lifecycle/query support or orphan removal
is added. D24 owning behavior is unchanged; see the dated D25/TCK evidence.

== Simple-parent MapsId derived identity (D23, 2026-10-16)

The existing P5 mappings now have a strengthened bounded contract:

* Owning `@OneToOne` with unnamed `@MapsId`: dependent simple
  `@Id` and parent simple ID have matching types.
* Owning `@ManyToOne`/`@OneToOne` with `@MapsId("parentId")`: one direct BASIC component of a dependent
  `@EmbeddedId` matches the parent's simple ID. Other components are supplied by
  the application. Mutable and record key classes are covered.

Annotations and metadata-complete `orm.xml` (`maps-id=""` or
`maps-id="parentId"`) use the same model and generated accesses.
The association owns the shared PK/FK columns; derived scalar attributes are
not additional writable columns. Initial values come from the parent.
Sequence-cascaded IDs are available after persist/merge; IDENTITY values are
finalized before the dependent INSERT and PostPersist. No generated primitive
zero placeholder is registered or cached as an actual dependent key.

An identity cannot be changed or cleared after registration, including before
first flush, inside PreUpdate or through bulk identity SET. Ordinary updates and
dependent-first deletes remain supported. Direct writes to relationship-mapped
embedded-ID components are ignored and rederived (their specification-defined
read-only semantics); refresh restores them before snapshots and PostLoad.
Missing parent identity and incomplete
remaining key components fail before the dependent INSERT.
Incoming FKs and generated DDL use actual derived column names and underlying
BASIC key types. ID/FK loads, JPQL/Criteria navigation/comparison, fetch joins/
graphs, caches and callbacks agree on the tuple. MapsId relationships retain
the existing eager fallback, even for otherwise interceptable LAZY properties.

Bootstrap explicitly refuses unknown/dotted names, incompatible types, named
MapsId on a simple ID, whole-ID many-to-one (OneToOne is required by §2.4.2.1),
inverse/collection/join-table mappings, overlapping key
parts, independently generated dependent IDs, noninsertable/secondary-table
join columns, chained targets and unsupported nested target/remaining key
shapes. Existing P5 exact matching flat composite-parent examples remain
supported; D23 does not imply arbitrary nested/composite/partial key support,
incoming joins to nested composite-derived keys or broader optimized loading.
See the detailed Persistence roadmap and `TCK.md` for the exact evidence.

== Secondary-table business-key to-one joins (D26, 2026-10-17)

D26 extends the historical D22 boundary below to *one* immutable, non-null,
insertable, unique non-ID BASIC column in a declared target secondary table.
Owning `ManyToOne`/`OneToOne`, `SecondaryTable`/`SecondaryTables`,
metadata-complete ORM XML and existing converters use the same mapping/access
planner. The target primary key and secondary PK join must each have one
column; a renamed secondary PK join is resolved from metadata.

Persistence 3.2 §11.1.26 makes non-PK references optional and explicitly
*nonportable between providers*. Table 24 places the referenced column in the
target entity's table; §11.1.47 allows its state across primary/secondary tables.
Noether requires an unambiguous column-to-table mapping.
`JoinColumn.table` remains the *owner's FK table*, not a target-table selector.
Duplicate target column names are refused, never guessed.

The unique declaration must be `Column(unique=true)` or an exact
`SecondaryTable.uniqueConstraints`/XML secondary-table constraint.
A primary-table or other-secondary-table constraint does not qualify.
Generated DDL references the actual secondary unique column. Reads resolve the
secondary PK join back to the target's primary identity; writes and converted
values use the existing generated accesses/binders. Persist/generated identity,
reassignment/null, flush/delete, JPQL/Criteria joins/navigation/projections/
identity comparisons, bulk association SET and cache identity retain ordinary
semantics. A closed-module APT property-access regression needs no package opens.

Fetch/load graphs and explicit fetch joins retain complete ordinary eager
loading. D10 lazy-reference, D13 batching and D11–D21 optimized collectors are
not widened. No new FK-cycle ordering is introduced.

Composite secondary business tuples or target PK/secondary PK joins, owner
secondary-table FKs, primary-table business references on multi-table targets,
inheritance, join tables, embedded/derived business relationships, mutable/
nullable/nonunique/ambiguous keys and inverse business collections stay refused.
Ordinary primary-key references are unchanged. See the prioritized roadmap and
xref:tck.adoc[D26 verification]; D5/D9–D25 evidence remains historical.

== Querying to-one references in element collections (D27, 2026-10-17)

JPQL and Criteria can navigate an owning to-one association inside a collection
embeddable to target attributes, compare the entity by identity, and project the
associated entity itself. Explicit joins from the element alias to the target
support both inner and left joins. This works through nested embeddable values
and metadata-complete ORM XML as well as annotations.

Selecting the association directly uses its collection-row FK as the target's
actual simple identity, preserving null association rows. Navigating target
attributes or declaring a join uses the mapped FK and target identity through the
SQL AST. No lazy-reference, collection-fetch, graph, or batching optimization is
added; ordinary collection loading is unchanged. Broader mapping/query shapes
remain separate work; see the D27 contract and test evidence in the Persistence
roadmap.

== Projecting relationship-bearing element values (D28, 2026-10-17)

JPQL and Criteria can select an entire supported collection embeddable value,
including nested embeddables and owning to-one attributes. Each relationship is
resolved from its collection-row FK to the actual managed target entity, so
repeated references share persistence-context identity and nullable associations
remain null. This covers list and map values with annotation and metadata-complete
XML mappings.

This enables value projection only: whole-value comparisons involving
relationships, unsupported D24 mapping shapes, and collection fetch, graph,
lazy-reference, or batching optimizations remain outside this support.

== Unique business-key to-one joins (D22, 2026-10-16)

D22 prioritizes relational mapping over further graph optimization.
An owning `ManyToOne` or `OneToOne` may reference single/composite *non-ID BASIC*
columns, for example `Order.customer_code -> Customer.code`, without changing
`Customer.id` as the JPA identity. Annotation, metadata-complete ORM XML and
annotation/XML overrides use the same planner, generated accesses and binders,
including converters and explicit composite-column ordering.

Referenced columns must be unambiguous primary-table attributes with
`nullable=false`, `insertable=true`, `updatable=false`, and either single-column
`unique=true` or an exact table `uniqueConstraints` tuple. Composite join columns
must explicitly name every referenced column and have uniform nullability and
writeability; owning join columns must be fully insertable/updatable.
Read-only/shared-column business joins are outside this bounded lot.
Missing, duplicate, nonunique, ID/business-mixed or mutable mappings
fail bootstrap. All-null nullable join tuples mean no target; partial-null tuples
fail at load. Managed key mutation is refused at flush with converter-aware dirty
checking. Detached references must agree with their actual managed identity.

Writes bind the business tuple. Reads first resolve the actual target identifier
and then use ordinary identity-based loading. Repeated references, `find`, refresh,
merge and L2 cache never key managed instances by a business value. Owning/inverse
one-to-one, reassignment/clearing, persist cascade, orphan removal, required
insert/delete ordering, self references and nullable cycles use the existing
lifecycle paths. Non-null dependency cycles are explicitly refused.
DDL foreign keys reference the actual unique target columns; table/XML unique
constraints are emitted as SQL constraints rather than unique indexes.

JPQL/Criteria joins, navigation, projections and association identity/null
comparisons follow this mapping. Bulk association SET accepts an existing entity
parameter/literal or NULL and checks target existence; arbitrary SET expressions
and referenced-key mutation are explicitly refused. Existing complex bulk-path
restrictions remain unchanged; bulk mutations still do not cascade orphan removal.

[IMPORTANT]
====
Business associations deliberately use eager/ordinary loading. Their owners
are excluded from D11–D21 optimized hydration/graph collectors and D13 batching,
and the business association is excluded from D10 lazy-reference eligibility,
even when getter-interceptable. Fetch joins and graph queries/finds still produce
complete state, without treating a foreign business tuple as an entity ID.
====

This bounded lot excludes join tables, secondary tables, inheritance, embedded
association paths, derived/unsupported nested identifiers, inverse business
collections and out-of-band or mutable business keys. These remaining mapping
boundaries precede deeper graph/lazy/batch optimization in the roadmap.
Historical D5/D9–D21 and BUG evidence is retained.

== Root to-one collection graphs (D21, 2026-10-16)

D21 supersedes D20's root-to-one-collection fallback for finite, acyclic root
to-one paths to hydratable collection owners, for example `customer.addresses`
or `customer.favorite.tags`. The D19/D20 eligible JPQL/Criteria query shapes
(one concrete root, optional DISTINCT, no explicit joins/grouping/having/set/
additional selections or locking) and non-locking find retain their boundaries.
FETCH and LOAD graphs, independent root collections, element to-one subgraphs
and at most *two collection edges per graph path* are supported.

A bounded collection-free LEFT to-one seed discovers intermediate owners before
the existing collectors run. Compatible requests shared between collection
depths merge at the later depth. IDs are deduplicated across roots/branches;
null to-ones create no owner IDs, and empty owner sets issue no collection SELECT.
For each seed/collector, `B = min(fetch.batch-size, floor(512 / owner-key-width))`.
An eligible query uses
`1 + ceil(Nroot / Broot) + sum(ceil(Nc / Bc))` SELECTs; a database find
omits the first root-identity SELECT. The seed is not a third collection edge.
Counts exclude ordinary completion of dirty reassigned relationships and unsupported
lazy mappings. Root-only SQL pagination precedes complete seed/collection reads.

All branches complete before snapshots/cache publication and once-per-new-identity
callbacks. Dirty entities/collections, in-place wrappers/references, ordered/null/
duplicate/list/map contents, flush and no find auto-flush are retained.
Complete managed/cache finds need neither SELECT nor a new JDBC connection.
Mutable graphs and hint replacement are planned per execution.

Explicit cyclic/type-revisiting paths, a third collection edge, unsupported mapped
eager closures, polymorphic/non-hydratable owners or targets, unsupported keys and
embedded paths and the earlier complex/locking query/find shapes retain complete
fallback or explicit refusal. Existing pagination guards, explicit fetch joins and
earlier graph eligibility are unchanged. Deeper/cyclic graph optimization, broader
fetch/lazy/batch eligibility and missing mappings remain separate priorities.

== Lazy read batching

[cols="3,1,4"]
|===
| Factory property | Default | Values
| `io.vidocq.noether.jpa.fetch.batch-size` | `16`
| Integer `1`–`256`; `1` disables grouping. Invalid/blank values fail factory creation.
|===

Independent of JDBC _write_ batching (`io.vidocq.noether.jpa.jdbc.batch-size`).
Read groups have at most 512 key parameters; composite owner keys reduce the group
size. The requested pending identity is first, followed by compatible context entries
in registration order. No detached, removed, already initialized or dirty initialized
objects are enrolled.

Eligible: single-table, non-polymorphic collection owners and entity targets; element
collections, owning join-table/target-FK collections and inverse target-FK collections;
to-one references satisfying the existing D10 generated-subclass eligibility.
Entity-valued map keys, inverse join tables, inheritance/secondary tables and replaced
snapshot wrappers retain complete ordinary loading. Unsupported lazy to-one shapes
remain eager. This setting does not widen SQL fetch or entity-graph eligibility.

Batches use the active transaction connection or an ordinary read connection, without
auto-flush. Like the ordinary lazy loader they read the database, do not consult L2
per pending identity and do not force cache publication. Normal transaction publication
still applies; graphs containing unloaded to-one references remain excluded from L2.
Detach/clear/close behavior is unchanged. See xref:internals.adoc[] for hydration details.
