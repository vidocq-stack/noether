= Reference
:description: Noether artifacts and external integrations.

All Noether artifacts are under `io.vidocq.noether`:

[cols="2,3"]
|===
| Artifact | Role
| `noether-root` | Repository reactor
| `noether-jpa` | Persistence aggregator (directory `noether-persistence`)
| `noether-jpa-core` | Persistence provider
| `noether-jpa-dialect-spi` | SQL AST and dialect contract
| `noether-jpa-dialect-h2`, `noether-jpa-dialect-postgresql` | Dialect adapters
| `noether-jpa-processor` | APT and generated entity access
| `noether-jpa-cdi` | Vauban CDI and Mansart JTA bridge
| `noether-validation`, `noether-validation-core` | Provisional local-only Validation
|===

Java module names retain their suffixes under `io.vidocq.noether.jpa.*` and
`io.vidocq.noether.validation.*`. External dependencies stay under
`io.vidocq.mansart` and `io.vidocq.vauban`. `mansart.version` pins the independent
Mansart version. Integration vehicles and all provisional Validation artifacts
are excluded from release publishing.

== Query entity graph hints

[cols="2,4"]
|===
| Standard hint | Query SQL contract (D14)
| `jakarta.persistence.fetchgraph`
| Explicit eligible to-one nodes/subgraphs become LEFT fetch joins. Omitted eager
attributes may still be overfetched by the loader; they are not guaranteed unloaded.
| `jakarta.persistence.loadgraph`
| The same explicit nodes, plus eligible mapped eager to-ones (cycle-guarded expansion).
|===

If both hints are present, FETCH retains its existing precedence. Graph objects must
belong to the same persistence unit and match the query root under the existing
validation rules. Graph/hint changes are reread per execution.

SQL scope: one concrete-root entity selection, no distinct/grouping/locking/set query,
explicit collection fetch or conditional/treated joins. Unsupported target types,
embedded/treated graph nodes and collection nodes outside D16 below use complete existing follow-up
loading. Mixed graphs may combine same-row to-ones with complete collection reads.
No eager requirement is suppressed; D10 lazy eligibility and D13
batch bounds remain unchanged. See xref:internals.adoc[] for the shared hydration path.

== Find entity graph hints (D15, 2026-10-16)

The same standard hints drive eligible direct/nested to-one SQL for non-locking
database finds. Composite root keys, mapped converters and secondary-table columns
use existing binders/hydration. The 3.2 `find(EntityGraph, id, options)` overload is
equivalent to FETCH. Unlike queries, find retains its existing merged plan when both
validated graph hints are supplied. Mutable graph nodes are reread per invocation.
LOAD includes eligible eager to-ones; FETCH may overfetch omitted eager state.

Managed-instance and L2 cache hits retain their fast paths and graph initialization;
unloaded references hydrate in place, dirty state is not overwritten and find never
auto-flushes. Existing retrieve/store/BYPASS/REFRESH, lock/timeout and refresh semantics
are unchanged. Plain/locking finds, unsupported polymorphic/inherited types and
unsupported graph paths retain ordinary loading. Collection nodes outside D16 below
use complete follow-up loading.

== One leaf collection graph (D16, 2026-10-16)

Both graph hints can join one explicitly requested root collection through the
existing collection-fetch assembler. Eligible queries select one concrete root,
optionally DISTINCT, with no existing joins, grouping/having, set operations or locks.
Eligible non-locking database finds use the same path, including unloaded managed roots.
Basic graph attribute nodes may coexist, but explicit to-one association nodes and
(at D16 delivery) all subgraphs retain D14/D15's existing loading instead; D17 below
adds to-one subgraphs on the collection.

The join is LEFT: empty owners remain and null element rows remain distinguishable
from absence. Synthetic graph joins do not duplicate query roots. Entity, basic and
embeddable collections retain duplicate bags, list positions/order, sorted sets and
supported basic/derived map keys. Collections complete before snapshots/callbacks/cache;
managed dirty state and wrapper/target identity are preserved. Other mapped eager state
remains loader work, including LOAD requirements and permitted FETCH overfetch.

Finite owner pagination pages distinct owners in SQL, then loads their whole collections
through secondary reads. Unsupported collection paging throws before SQL; no silent
in-memory pagination or partial collection. Explicit JOIN FETCH semantics are unchanged.
Managed/cache find hits keep their fast paths; find does not acquire query auto-flush.
Mutable graphs and replacement hints are reread on every execution.

Multiple collections, nested-to-one collection subgraphs, mixed to-one nodes,
extra/filtering joins, complex/polymorphic/inherited shapes, embedded/treated paths,
and entity/embeddable map keys keep complete existing fallbacks. Nested/multiple
collection SQL is future work, not a Cartesian-product expansion.

== One collection with to-one subgraphs (D17, 2026-10-16)

The single graph-requested root collection of D16 may carry an element subgraph, when the
collection is entity-valued and the subgraph holds only direct or nested to-one nodes
(for example `lines { product { supplier, category } }`) to concrete, non-polymorphic
entities, plus basic/embedded leaves. Every to-one becomes a LEFT fetch join from the
collection alias, and owner, element and targets are hydrated from the same rows. LOAD
also joins the elements' mapped eager to-ones; FETCH may overfetch omitted eager state.
The same query/find shapes as D16 apply.

Null targets never filter elements; empty owners, null elements, bag duplicates, list
positions and basic/derived map keys are preserved; shared targets keep one managed
instance. Dirty managed entities and collections are not overwritten, unloaded lazy
references complete in place, and `PostLoad` runs once per fresh entity after the
whole graph is assembled; callback mutations remain dirty and failures propagate.
Finite owner pagination pages distinct owners in SQL without the graph joins, then loads
collections and subgraphs through complete secondary reads.

Multiple collections, collection-valued nodes inside the subgraph (including element
collections of targets), polymorphic/inherited targets, embedded subgraphs, root to-one
nodes beside the collection and the D16 query/map-key restrictions keep the complete
existing fallback. Explicit JOIN FETCH semantics are unchanged.

== Lazy read batching

[cols="3,1,4"]
|===
| Factory property | Default | Values
| `io.vidocq.noether.jpa.fetch.batch-size` | `16`
| Integer `1`–`256`; `1` disables grouping. Invalid/blank values fail factory creation.
|===

Independent of JDBC _write_ batching (`io.vidocq.noether.jpa.jdbc.batch-size`).
Read groups have at most 512 key parameters; composite owner keys reduce the group
size. The requested pending identity is first, followed by compatible context entries
in registration order. No detached, removed, already initialized or dirty initialized
objects are enrolled.

Eligible: single-table, non-polymorphic collection owners and entity targets; element
collections, owning join-table/target-FK collections and inverse target-FK collections;
to-one references satisfying the existing D10 generated-subclass eligibility.
Entity-valued map keys, inverse join tables, inheritance/secondary tables and replaced
snapshot wrappers retain complete ordinary loading. Unsupported lazy to-one shapes
remain eager. This setting does not widen SQL fetch or entity-graph eligibility.

Batches use the active transaction connection or an ordinary read connection, without
auto-flush. Like the ordinary lazy loader they read the database, do not consult L2
per pending identity and do not force cache publication. Normal transaction publication
still applies; graphs containing unloaded to-one references remain excluded from L2.
Detach/clear/close behavior is unchanged. See xref:internals.adoc[] for hydration details.
