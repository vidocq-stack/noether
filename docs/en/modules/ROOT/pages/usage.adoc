= Usage
:description: Configuring and using Noether: persistence units, connections, entities, queries, loading, CDI, Vidocq and application servers.
:page-aliases: modules/noether-persistence.adoc

[.lead]
Noether is used through the standard Jakarta Persistence API: nothing in your code names Noether except the
`<provider>` of a unit. This page goes through the tasks of an application, from declaring a unit to deploying it
on a server. xref:getting-started.adoc[Getting started] builds a complete application first; the properties are
listed in xref:reference.adoc#properties[Reference].

[#units]
== Declaring persistence units

A unit is declared in `META-INF/persistence.xml` (versions 1.0 to 3.2), or in code with `PersistenceConfiguration`
(see xref:getting-started.adoc[Getting started]). A unit declared in code manages only the classes given to
`managedClass(...)` and those of its mapping files, and `noether-jpa-cdi` does not see it. Name Noether as the
provider:

[source,xml]
----
<provider>io.vidocq.noether.jpa.core.NoetherPersistenceProvider</provider>
----

A unit manages:

* the classes its `<class>` elements list;
* the classes its mapping files declare: `<mapping-file>` elements, and `META-INF/orm.xml` when it exists;
* the classes of the `<jar-file>` elements;
* unless `<exclude-unlisted-classes>` is set, every entity, embeddable, mapped superclass and converter of the unit's
  root, the directory or jar that holds `META-INF/persistence.xml`.

Each jar or directory of the application may carry its own `META-INF/persistence.xml`, so a Maven module, and the
Java module it builds, can declare the units of its own entities: Noether reads every file, and a unit scans only its
own root. A unit name is unique across all these files: two units of one name, in one file or in two, fail with a
`PersistenceException` that names the files.

A file can declare several units. Two units of the same root that do not exclude their unlisted classes both manage
every class of that root: with schema generation, each creates every table in its own database. List the classes
of each unit and exclude the others:

[source,xml]
----
<persistence-unit name="ledger">
    <class>com.acme.ledger.Entry</class>
    <exclude-unlisted-classes>true</exclude-unlisted-classes>
</persistence-unit>
<persistence-unit name="archive">
    <class>com.acme.ledger.Note</class>
    <exclude-unlisted-classes>true</exclude-unlisted-classes>
</persistence-unit>
----

The properties of a unit come from its `<properties>`, overridden by the map passed to
`Persistence.createEntityManagerFactory(name, map)`.

[#unit-sources]
=== Units declared by a runtime

A runtime can declare units from its own configuration, beside the `persistence.xml` files: it implements
`io.vidocq.noether.jpa.core.spi.PersistenceUnitSource` and provides it, with `provides ... with ...` in its
`module-info.java` or a `META-INF/services` entry on the class path. Noether finds the sources in its own module
layer, in its own class loader (a build tool that runs Noether on its class path, as `vidocq:generate` does), then
through the application's class loader. Noether reads no key of any runtime. It asks every source wherever it looks
for units, in the provider and in `noether-jpa-cdi`. The Vidocq runtime declares the
units of its `vidocq.persistence."<unit>".*` keys this way (Vidocq/vidocq#551).

A source returns one `PersistenceUnitDeclaration` per unit. Its attributes fall in two groups:

* Those that declare the unit, what a `persistence.xml` would say: its root, the packages of that root it is restricted
  to (with their sub-packages), the classes it lists (then those alone, as with `<exclude-unlisted-classes>`), its
  transaction type, qualifiers and scope. A unit of the same name in a `persistence.xml` or in another source fails
  with the duplicate `PersistenceException`, which names the file and the source.
* Those that override it: its data source, which is the JTA data source of a JTA unit and the non-JTA one of a
  resource-local unit, its JTA and non-JTA data sources by name, and its properties, which differ between deployments. A
  declaration that sets only these overrides the unit of that name that a `persistence.xml` declares, its properties
  winning over the file's. When no file declares the unit, the declaration declares it, at its default root and
  with its default transaction type, which declare nothing themselves.

A declaration made _when alone_ is a runtime's default unit: it is declared only when the application declares no
other unit and its root holds an entity, an embeddable, a mapped superclass or a converter.

What a declaration leaves out takes the default of a `persistence.xml`: `RESOURCE_LOCAL`, an unspecified shared
cache mode, validation mode `AUTO`, `META-INF/orm.xml` when the root has one. A source is asked each time the units
are looked for: at build when a container freezes its beans (`vidocq:generate`), and at start when the provider
creates a factory. The runtime keeps the two consistent.

[#connections]
== Connections

A unit gets its connections in one of three ways:

[cols="1,2,2"]
|===
| Source | How | Typical setting

| JDBC properties
| `jakarta.persistence.jdbc.url`, `.user`, `.password`, and `.driver` when the driver is not found by its URL
| Java SE, tests

| A `DataSource` object
| `jakarta.persistence.nonJtaDataSource` (or `jakarta.persistence.dataSource`) in the map of
  `createEntityManagerFactory`
| An application that owns its pool

| A container's data source
| `<jta-data-source>` and `<non-jta-data-source>`: a JNDI name on an application server, the name of a `@Named`
  `DataSource` bean with `noether-jpa-cdi`
| Jakarta EE servers, CDI containers, Vidocq
|===

In Java SE, `<jta-data-source>` and `<non-jta-data-source>` cannot be resolved (there is no JNDI): use the JDBC
properties, or pass the `DataSource` object.

*Pooling JDBC-property units.* Add `noether-jpa-pool-mansart` at run time and Noether pools the connections of a unit
configured by `jakarta.persistence.jdbc.*`; the pool closes with the factory. Without it, each transaction opens its
own connection, and the factory says so in one `INFO` line.

[cols="2,1,3"]
|===
| Property | Default | Meaning

| `io.vidocq.noether.jpa.pool.max-size` | `10` | Most connections open at once.
| `io.vidocq.noether.jpa.pool.min-idle` | `0` | Connections kept open while idle.
| `io.vidocq.noether.jpa.pool.acquire-timeout` | `PT5S` | How long a caller waits for a connection (ISO-8601).
| `io.vidocq.noether.jpa.pool` | | `false` turns the pool off for this unit.
|===

A `DataSource` passed to Noether is used as it is: Noether neither pools it nor sizes it.

[#entities]
== Entities and their access

Compile the entities with `noether-jpa-processor`, as in xref:getting-started.adoc#pom[Getting started]. Then:

* *On the module path*, the module of the entities declares what the processor generated, one line per entity
  package (the processor prints it, and the factory names it when it is missing):
+
[source,java]
----
provides io.vidocq.noether.jpa.core.spi.ManagedAccessProvider
    with com.acme.shop.model._NoetherJpaAccess;
----
* *On the class path*, there is nothing to declare: the processor registers the accesses in `META-INF/services`.
* *Entities compiled without the processor* (a third-party jar) get their access when the factory starts. On the
  module path, their package must be open to Noether: `opens com.acme.shop.model to io.vidocq.noether.jpa.core;`.

Annotations and `orm.xml` mapping files both work, together or alone (`metadata-complete`). Records are supported
as embeddables. See xref:concepts.adoc#entity-access[Entity access].

*Identifiers.* `IDENTITY`, `SEQUENCE`, `TABLE`, `UUID` and `AUTO` are supported. `AUTO` is a `UUID` for a `UUID`
identifier, the named sequence when the generator names one, and otherwise a table generator: table `SEQUENCE`,
columns `SEQ_NAME` and `SEQ_COUNT`, blocks of 50. A table generator allocates its blocks on a connection of its own,
committed on its own, so the unit needs two connections at once: a Noether pool below two connections is refused,
and a JTA unit allocates through its `<non-jta-data-source>`, which it then must have.

== Reading and writing

Jakarta Persistence 3.2 runs a unit of work in one call:

[source,java]
----
factory.runInTransaction(em -> em.persist(new Book("Moderne Algebra", 1930)));

Book book = factory.callInTransaction(em -> em.find(Book.class, id));
----

Both open an entity manager, begin a resource-local transaction, run the lambda, commit, and close the entity
manager; an exception rolls back. The classic form works the same:

[source,java]
----
try (var em = factory.createEntityManager()) {
    var tx = em.getTransaction();
    tx.begin();
    try {
        Book book = em.find(Book.class, id);
        book.setTitle("Moderne Algebra I");    // written at commit: no call to save
        tx.commit();
    } finally {
        if (tx.isActive()) tx.rollback();
    }
}
----

`persist`, `find`, `getReference`, `merge`, `remove`, `refresh`, `detach` and their cascades behave as the
specification says. Optimistic locking uses `@Version`; pessimistic locks (`PESSIMISTIC_READ`,
`PESSIMISTIC_WRITE`, `PESSIMISTIC_FORCE_INCREMENT`) lock the rows they read with `SELECT … FOR UPDATE`, or
`FOR SHARE` for `PESSIMISTIC_READ` on PostgreSQL (H2 has no shared row lock and takes `FOR UPDATE`).

`jakarta.persistence.lock.timeout` and `jakarta.persistence.query.timeout` can be set in `persistence.xml`, on the
factory, on the entity manager, or on one operation: a hint of `find`, `lock`, `refresh` or a query, or
`setTimeout`. The narrowest wins. A query takes the timeouts of its entity manager when it is created.

[#queries]
== Queries

*JPQL*, with named or positional parameters and pagination:

[source,java]
----
List<Book> page = em.createQuery("""
        select b from Book b
        where b.published between :from and :to
        order by b.title""", Book.class)
    .setParameter("from", 1920)
    .setParameter("to", 1935)
    .setFirstResult(20).setMaxResults(10)
    .getResultList();
----

*Criteria*, typed with the canonical metamodel the processor generates (`Book_`):

[source,java]
----
var cb = em.getCriteriaBuilder();
var query = cb.createQuery(Book.class);
var book = query.from(Book.class);
query.where(cb.lessThan(book.get(Book_.published), 1925))
     .orderBy(cb.asc(book.get(Book_.title)));
List<Book> early = em.createQuery(query).getResultList();
----

*Named queries* come from `@NamedQuery`, `<named-query>` in `orm.xml`, or `addNamedQuery`, and are created with
`createNamedQuery`. *Native queries* (`createNativeQuery`) are sent as written, with result
mappings (`@SqlResultSetMapping`) and stored procedures (`createStoredProcedureQuery`).

JPQL supports the 3.2 language: joins and fetch joins, `TREAT`, `TYPE`, subqueries, constructor expressions
(`select new`), set operations (`union`, `intersect`, `except`), bulk `update` and `delete`, and the 3.2 functions.
A constructor expression or a `@ConstructorResult` calls a public constructor of a class that need not be an entity;
Noether looks the constructor up once per class, not per row. A stored-procedure query created outside a transaction
runs in the transaction that is current when it executes.

[#loading]
== Loading relationships

Collections are lazy by default and to-one references are lazy when their target allows it (see
xref:concepts.adoc#lazy[What `LAZY` means]). To load what a use case needs in one go:

* a fetch join: `select o from Order o join fetch o.lines where o.id = :id`;
* an entity graph, passed as the `jakarta.persistence.fetchgraph` or `loadgraph` hint of a query or of `find`
  (see <<entity-graphs,Entity graphs>>);
* `FetchType.EAGER` on the mapping.

The first access to an unloaded collection or reference loads the other pending ones of the same kind in the same
statement, up to `io.vidocq.noether.jpa.fetch.batch-size` (`16` by default, from `1` to `256`; `1` turns batching
off). The batch runs on the transaction's connection and does not flush pending changes first. It covers single-table,
non-polymorphic mappings; the others load each collection or reference on its own.

A collection that was never loaded cannot be loaded once its owner is detached: it throws `PersistenceException`.
Load it while the entity manager is open.

[#entity-graphs]
=== Entity graphs

An entity graph names what a query or a `find` loads with its result:

[source,java]
----
var graph = em.createEntityGraph(Order.class);
graph.addSubgraph("customer").addAttributeNodes("address");
var orders = em.createQuery("select o from Order o order by o.id", Order.class)
    .setHint("jakarta.persistence.fetchgraph", graph)
    .setMaxResults(20)
    .getResultList();

var lines = em.createEntityGraph(Order.class);
lines.addAttributeNodes("lines");
var order = em.find(Order.class, id, Map.of("jakarta.persistence.loadgraph", lines));
var same = em.find(lines, id);         // the typed overload of 3.2 applies the graph as a fetch graph
----

* *To-one nodes*, direct or nested, are read in the query's own SQL through left joins: an owner without a target
  stays in the result.
* *Collection nodes* of a query are read after the root query, one grouped statement per collection, so a page is cut
  on the owners in SQL and every collection comes back complete. A path may hold up to three collection edges, starting at a
  root collection (`lines.discounts.tags`) or behind root to-ones (`customer.addresses`).
* *`loadgraph`* also loads the attributes mapped `EAGER`. *`fetchgraph`* loads the nodes of the graph, but does not
  promise that an `EAGER` attribute it leaves out stays unloaded. When a query gets both hints, the fetch graph wins;
  `find` merges them.
* *`find`* applies a graph when it reads the database without a lock. An entity already in the persistence context or
  in the second-level cache is not read again: what the graph adds is loaded, and its changes are kept.
* *Other shapes* (a fourth collection edge, a path that comes back to a type, a polymorphic root, a query with
  grouping, a lock, set operations or fetch joins of its own) are loaded completely the ordinary way, or refused with
  an explicit error. A graph never yields a partial collection.

The exact shapes are in xref:reference.adoc#boundaries[Mapping and loading boundaries].

[#inheritance]
== Inheritance

`SINGLE_TABLE` (the default), `JOINED` and `TABLE_PER_CLASS` are supported, with annotations or `orm.xml`,
including polymorphic queries, `TYPE` and `TREAT`. Under `TABLE_PER_CLASS`, identifiers must be unique across the
hierarchy and `IDENTITY` is refused. Defaults and limits are in xref:reference.adoc#inheritance[Inheritance].

[#advanced-mappings]
== Advanced mappings

Noether supports some mappings beyond the common ones, each within explicit limits. A mapping outside them is refused
when the factory starts, never mapped another way. Each one's limits are in
xref:reference.adoc#boundaries[Mapping and loading boundaries]:

* *To-one joins on a business key* rather than the primary key: unique, immutable basic columns of the target (D22),
  or of one target secondary table, declared in that table's `uniqueConstraints` (D26, D43). Reference every column
  with `@JoinColumns`. `JoinColumn.table` names the owner's table, never the target's. This is optional support that
  other providers need not offer.
* *Relationships inside element collections*: an embeddable element may hold an owning to-one (D24), which queries
  navigate, compare and project like any other path (D27, D28).
* *Derived identities* of the targets of those elements: shared keys through `@MapsId` (D23, D30, D31, D37 to D42),
  composite keys (D29) and `@IdClass` keys whose parts are relationships (D32, D35, D36). A relationship part of an
  `@IdClass` has the type of the parent's identifier, not the parent entity. `@JoinColumns` name the target's columns,
  not the fields of its key class. Set the assigned key parts and the parents before `persist`.

== Schema generation

The standard `jakarta.persistence.schema-generation.*` properties create, drop or script the schema from the
mapping, a script, or both. `drop-and-create` suits tests; production databases are usually managed by migration
scripts, with `none` (the default).

[source,xml]
----
<property name="jakarta.persistence.schema-generation.database.action" value="drop-and-create"/>
<property name="jakarta.persistence.sql-load-script-source" value="META-INF/data.sql"/>
----

`EntityManagerFactory.getSchemaManager()` does the same from code: `create`, `drop`, `validate` (checks that the
mapped tables and columns exist) and `truncate` (empties the unit's tables and runs the load script again, handy
between tests).

== Second-level cache and Bean Validation

* *Second-level cache.* `<shared-cache-mode>` turns on the factory's cache: `ALL`, `ENABLE_SELECTIVE` (entities
  marked `@Cacheable`, also the behaviour of `UNSPECIFIED`), `DISABLE_SELECTIVE` or `NONE`. Changes are published
  to it only after their transaction commits. `jakarta.persistence.cache.retrieveMode` and `storeMode` apply to the
  entity manager, to `find` and `refresh`, and to a query (`setCacheRetrieveMode`, `setCacheStoreMode` or the
  hints). A query starts with the modes of its entity manager; `BYPASS` reads the database without publishing what it
  loads, `REFRESH` replaces the cached state with the database's.
* *Bean Validation.* With a Jakarta Validation provider on the path, entities are validated before persist and
  update (`<validation-mode>` `AUTO`, the default). `CALLBACK` makes a missing provider an error, `NONE` turns
  validation off. Noether's own `noether-validation` is a test stopgap, not published: bring a provider.

[#cdi]
== With CDI

`noether-jpa-cdi` is a CDI 4.1 build compatible extension, so it needs no API of a particular container. It is
tested on Vauban, on Quarkus ArC and in the Vidocq runtime. It injects the units of `persistence.xml`, and those of
the xref:#unit-sources[unit sources]:

[source,java]
----
@ApplicationScoped
public class Library {

    @PersistenceContext(unitName = "library")
    EntityManager em;                  // container-managed, transaction-scoped

    @PersistenceUnit(unitName = "library")
    EntityManagerFactory factory;      // closed by the container, not by the application

    @Transactional
    public void add(Book book) {
        em.persist(book);
    }
}
----

`unitName` may be left out when the application has one unit. `@PersistenceContext` gives transaction-scoped or
extended, synchronized or unsynchronized entity managers.

*JTA units* run on what the container provides, through `noether-jpa-jta`: a `TransactionSynchronizationRegistry`
bean, and a `DataSource` bean whose connections the container enlists in its transactions — the bean `@Named` after
the unit's `<jta-data-source>`, or the `@Default` one. Quarkus and Jakarta EE servers have both beans, and the
Vidocq runtime brings them. Details, including `TABLE` identifiers and connection sharing, are in
xref:reference.adoc#cdi-jta[Reference].

*On Vauban*, put `noether-jpa-cdi` on the annotation processor path next to `vauban-processor`, so that its build
compatible extension runs at build time, and boot with `VaubanContainer.builder().scanClasspath()`, which reads what
the build recorded.

[#inject-units]
=== Injecting a persistence unit with @Inject

Jakarta Persistence 3.2 lets a unit of `persistence.xml` name CDI qualifiers (`<qualifier>`, §8.2.1.5) and a CDI
scope (`<scope>`, §8.2.1.6). Jakarta EE 11 Platform §13.12 then makes the unit injectable with `@Inject`.
`noether-jpa-cdi` adds these beans for every unit of `persistence.xml` or of a unit source:

[source,xml]
----
<persistence-unit name="accounting" transaction-type="JTA">
    <qualifier>com.acme.Ledger</qualifier>
    <scope>jakarta.enterprise.context.RequestScoped</scope>
    <class>com.acme.Entry</class>
</persistence-unit>
----

[source,java]
----
@Inject @Ledger EntityManager entries;           // @RequestScoped here; @TransactionScoped without <scope>
@Inject @Ledger EntityManagerFactory factory;    // @ApplicationScoped, the bean named "accounting"
@Inject @Ledger CriteriaBuilder criteriaBuilder; // also PersistenceUnitUtil, Cache, SchemaManager, Metamodel
----

* **Qualifiers.** A unit without `<qualifier>` gives `@Default` beans. With two such units, an unqualified
  `@Inject EntityManager` is ambiguous: give the units qualifiers.
* **Scope.** Without `<scope>`, the `EntityManager` bean is `@TransactionScoped`, so the container must register
  that scope's context: `mansart-transactions-cdi` does, and the Vidocq runtime brings it. Outside a transaction, a
  call on that entity manager throws `ContextNotActiveException`.
* **The same unit as the Jakarta Persistence annotations.**
  - The entity manager is the one `@PersistenceContext` injects: in one transaction, both work on one persistence
    context.
  - The factory is the one `@PersistenceUnit` injects. The container closes it, and `close()` throws
    `IllegalStateException`.
* **Resource-local units.** A resource-local unit gets the factory beans but no `EntityManager` bean, because a
  container-managed entity manager is a JTA one (Jakarta Persistence 3.2, §7.6). Create its entity managers from the
  injected factory.
* **Bean names.** The `EntityManagerFactory` bean is named after its unit, so no other bean may have that name.
  For example, a data source bean `@Named("accounting")` and a unit `accounting` fail the deployment with a
  duplicate bean name. Give the data source another name, then name it in `<jta-data-source>`.
* **Errors.** A `<qualifier>` or `<scope>` that the deployment cannot load, or that is not a qualifier or a scope,
  fails the deployment with a `DefinitionException` that names the unit.
* **When the extension runs.** The beans come from the `persistence.xml` files and the unit sources the extension
  reads when it runs.
  - Vidocq runs it at build: `vidocq:generate` reads every `persistence.xml` of the application, and the start loads
    what the extension did (Vidocq/vauban#288), under `vidocq:dev` too. The start runs it instead on a test class
    path, after an IDE build that did not run `vidocq:generate`, or when the build could not complete it: two units of
    one name, for instance, make the build warn and the start fail.
  - A Vauban container built with `VaubanContainer.builder().addBeanClass(NoetherPersistenceExtension.class)` runs it
    at boot.
  - With `scanClasspath()`, Vauban replays what the build recorded. `vauban:generate` with `freezeExtensions`, the
    build step `vidocq:generate` runs too, reads `persistence.xml`; the annotation processor alone cannot, and these
    beans are then missing, while `@PersistenceContext` and `@PersistenceUnit` still work.
* **The start checks the units.** The extension hands the units it saw over to an observer of `Startup`, which
  compares them with the units of the start. A unit declared or gone since the beans were built, or a transaction
  type, qualifier or scope that changed, fails the start with a `DeploymentException` that names each difference and
  asks for a rebuild: a unit source that reads its configuration again at start cannot change the frozen beans. A
  build that saw no unit, as Vauban's annotation processor that reads no `persistence.xml`, checks nothing.

On Vauban, these beans need a `0.4.0-SNAPSHOT` built on 2026-11-13 or later, which holds Vidocq/vauban#286: it keeps
the scope an extension gives a bean, and unwraps the exceptions of an interface-typed normal-scoped bean (Vauban's
BUG-20261113-01 and BUG-20261113-02). Vauban `0.4.0-RC2` and earlier lack it.

[#vidocq]
== On Vidocq

The Vidocq runtime assembles Noether for you. The `noether-persistence` extension brings `noether-jpa-core`,
`noether-jpa-cdi`, the H2 and PostgreSQL dialects and Mansart Transactions; the units run on the data sources
declared in the Vidocq configuration. Every factory an injection point names is created when the application starts,
so a unit that cannot start fails the boot rather than the first request. See
xref:dev@vidocq::modules/vidocq-runtime-extensions.adoc#noether-persistence[the `noether-persistence` extension].

[#servers]
== Application servers

Noether runs unchanged where a container owns the transactions and the data sources:

* *Jakarta EE servers* (tested on Open Liberty). The server bootstraps the unit and injects `@PersistenceContext`
  itself. Turn on the server's persistence container without its own provider (on Open Liberty,
  `persistenceContainer-3.2` rather than `persistence-3.2`), deploy `noether-jpa-core`, `noether-jpa-jta` and a
  dialect in the WAR, and leave `noether-jpa-cdi` and `noether-jpa-pool-mansart` out. The exact dependencies and
  exclusions are in xref:reference.adoc#server-deployment[Deploying on an application server].
* *Quarkus.* Leave Quarkus' Hibernate ORM extension out, declare `noether-jpa-cdi`, a dialect, `quarkus-arc`,
  `quarkus-narayana-jta` and `quarkus-agroal`, configure the data source in `application.properties`, and declare
  the unit in `META-INF/persistence.xml`. See xref:reference.adoc#quarkus[Running on Quarkus].

In both, a JTA unit with `TABLE` identifiers (or `AUTO` resolved to a table generator) needs a
`<non-jta-data-source>` whose connections take part in no transaction.
