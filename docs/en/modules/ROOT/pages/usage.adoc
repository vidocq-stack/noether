= Usage
:description: Standard Jakarta Persistence bootstrap and generated access.

Use the standard `jakarta.persistence` API and entity annotations.
In `META-INF/persistence.xml`, the explicit provider is:

[source,xml]
----
<provider>io.vidocq.noether.jpa.core.NoetherPersistenceProvider</provider>
----

On the Java module path, declare generated-access providers with `provides
io.vidocq.noether.jpa.core.spi.ManagedAccessProvider with
your.package._NoetherJpaAccess;`. Generated-access entities do not require
reflective opens. Opaque entities using the Class-File API bootstrap path must
open their entity packages to `io.vidocq.noether.jpa.core`.

CDI/JTA integration uses `noether-jpa-cdi` and the external Mansart transaction
manager. The core does not import CDI, JTA or Vauban. See
xref:modules/noether-persistence.adoc[the detailed Persistence guide].

== Relationship-valued IdClass targets in collection elements

An embeddable element may hold an owning to-one to a target whose `@IdClass`
contains multiple relationship-valued parts (D35). Give each target relationship
an owning FK to a non-polymorphic parent; use the parent's ID type for
the corresponding field in the IdClass, not the parent entity type. Other parts
remain BASIC. D36 adds parents with direct all-BASIC `@EmbeddedId` or `@IdClass`
keys alongside simple IDs; use that parent key class for the relationship-named
IdClass field. Explicit element `@JoinColumns` reference the target's physical
FK/basic columns, not the IdClass field names.

The collection row stores the full tuple and resolves the target's managed
identity. JPQL/Criteria navigation, target/whole-value projection, duplicates
and null references retain their ordinary semantics. Owner/value mappings may
use metadata-complete ORM XML, but relationship-valued target identifiers remain
annotation-mapped. Nested/non-BASIC/chained parent identities and broader optimized
fetch/lazy/batch loading are not added. See xref:reference.adoc[Reference] for
the exact D32/D35/D36 mapping boundaries.

== Multiple MapsId components in collection targets

An element-value owning to-one may target an entity with a direct all-BASIC
`@EmbeddedId` whose distinct components are derived by separate
`@MapsId("componentName")` owning to-one relationships (D37).
Each parent must have a simple ID and be non-polymorphic; the named component
must use that ID's Java type. Other key parts remain application-supplied.
Generated parent IDs are propagated by the normal persist lifecycle before
collection rows bind the target's complete physical FK tuple.

The full mapping may use annotations or metadata-complete ORM XML. Repeated
references resolve one managed target; query projections/navigation and normal
collection rewrites, merge, refresh and shared-cache reads retain their semantics.
Overlapping mappings, nested/non-BASIC keys and composite/chained parents are
not included, and no fetch/lazy/batch optimization is widened.

== Whole composite MapsId collection targets

D38/D39 also permit an element-value owning to-one to reference a dependent with
a whole direct all-BASIC `@EmbeddedId` shared through an owning
`@OneToOne @MapsId` without a component name. The parent must use the same
key class through a direct all-BASIC `@EmbeddedId` or `@IdClass` and be
non-polymorphic, without derived identity. Parent identifier declaration order
need not match the embedded key's order; values are copied by generated
attribute access, not physical tuple position.
Reference the dependent's physical PK/FK columns in the element's
`@JoinColumns`, not necessarily the embedded key's default column names.
Both annotations and metadata-complete XML use the normal persist, query,
merge/refresh and cache paths. Named-component composite-parent derivation
beyond D40 below, general nested/chained keys and broader loading optimizations
are not included.

== Named composite MapsId collection targets

D40 permits one named embedded component of a collection relation target's
`@EmbeddedId` to derive from an owning `@ManyToOne` or `@OneToOne`
`@MapsId("componentName")`. The parent must be non-polymorphic and have a
direct all-BASIC `@EmbeddedId` of that component's Java type. All other target
key parts are BASIC. Supply those remaining parts and the parent before persist;
normal cascade ordering derives the component before collection rows are bound.

Element `@JoinColumns` reference the dependent's physical parent-FK columns
and remaining BASIC key columns. Default joins also use that complete tuple.
Annotations and metadata-complete ORM XML use the same generated access, query,
merge/refresh and shared-cache paths; mutable and record outer key classes work.
Named IdClass parents, multiple composite components, unmapped nested remainder,
deeper/chained parent keys and broader loading optimizations are not included.

== Query entity graphs

Both JPQL and Criteria entity queries accept standard graph hints:

[source,java]
----
var graph = em.createEntityGraph(Order.class);
graph.addSubgraph("customer").addAttributeNodes("address");
var orders = em.createQuery("select o from Order o order by o.id", Order.class)
    .setHint("jakarta.persistence.fetchgraph", graph)
    .setFirstResult(0).setMaxResults(20).getResultList();
----

Eligible direct and nested to-ones are hydrated from the query's LEFT-joined rows,
without filtering null targets. `loadgraph` additionally includes mapped eager to-ones;
`fetchgraph` only contributes explicit nodes to SQL but may still overfetch eager state
through the loader. It does not guarantee omitted eager attributes remain unloaded.
Graph/hint changes are honored on query reuse.

This is bounded to one concrete-root entity selection without distinct/grouping/locking,
set operations, explicit collection fetches or conditional/treated joins. Unsupported
graph nodes retain complete follow-up reads. D16 additionally supports one leaf root
collection (including DISTINCT queries) without existing joins:

[source,java]
----
var graph = em.createEntityGraph(Order.class);
graph.addAttributeNodes("lines");
var orders = em.createQuery("select o from Order o order by o.id", Order.class)
    .setHint("jakarta.persistence.loadgraph", graph).getResultList();
var order = em.find(Order.class, id, Map.of("jakarta.persistence.fetchgraph", graph));
----

Empty owners stay present and collections are complete. Finite query pages use SQL
owner paging plus complete secondary reads. At D16, subgraphs on the collection, multiple
collections and mixed explicit to-one graph nodes retain existing complete loading.
See xref:reference.adoc#_one_leaf_collection_graph_d16_2026_10_16[] for exact boundaries.
D17 adds to-one subgraphs on that collection, loaded in the same SELECT:

[source,java]
----
var graph = em.createEntityGraph(Order.class);
graph.addSubgraph("lines").addSubgraph("product").addAttributeNodes("supplier");
var orders = em.createQuery("select o from Order o", Order.class)
    .setHint("jakarta.persistence.fetchgraph", graph).getResultList();
----

Multiple root collections use independent grouped SQL reads (D19):

[source,java]
----
graph.addAttributeNodes("payments");
// Re-execution replans the mutable graph and reads complete lines and payments separately.
var withPayments = em.createQuery("select o from Order o", Order.class)
    .setHint("jakarta.persistence.loadgraph", graph).getResultList();
----

Two collection edges beginning at a root collection use grouped split reads (D20):

[source,java]
----
graph.addSubgraph("lines").addSubgraph("discounts").addAttributeNodes("supplier");
// The root query pages only orders; lines and their discounts are then read completely.
var page = em.createQuery("select o from Order o order by o.id", Order.class)
    .setHint("jakarta.persistence.fetchgraph", graph).setMaxResults(20).getResultList();
var order = em.find(Order.class, id, Map.of("jakarta.persistence.loadgraph", graph));
----

Finite element-to-one chains may lead to the second collection's owners, for example
`lines.product.tags`. D21 also groups collections reached through finite root to-one
chains, without adding a third collection edge:

[source,java]
----
var customerGraph = em.createEntityGraph(Order.class);
customerGraph.addSubgraph("customer").addSubgraph("addresses").addAttributeNodes("country");
var orders = em.createQuery("select o from Order o order by o.id", Order.class)
    .setHint("jakarta.persistence.loadgraph", customerGraph).setMaxResults(20).getResultList();
var orderWithAddresses = em.find(Order.class, id,
    Map.of("jakarta.persistence.fetchgraph", customerGraph));
----

Shared customers are grouped by distinct identity, not read once per order.
Null customers retain their orders; empty address collections remain complete.
Independent root collection branches and element to-one subgraphs may coexist.
The owner seed and every required collection stage complete before callbacks.
D33 adds a third edge to nested collection paths that begin at a root collection:

[source,java]
----
var deepGraph = em.createEntityGraph(Order.class);
deepGraph.addSubgraph("lines").addSubgraph("discounts").addAttributeNodes("tags");
var deepOrders = em.createQuery("select o from Order o order by o.id", Order.class)
    .setHint("jakarta.persistence.fetchgraph", deepGraph).setMaxResults(20).getResultList();
----

Each collection edge is read separately after SQL-only root pagination; callbacks
run after the third-level values are complete. D34 also supports three collection
edges on paths reached through a root to-one, such as
`Order.customer.recommendations.bundles.labels`. Explicit type-revisiting cycles,
a fourth edge and unsupported polymorphic/complex targets retain complete
ordinary loading or established explicit refusal.
See xref:reference.adoc#_two_collection_graph_edges_d20_2026_10_16[].
See xref:reference.adoc#_root_to_one_collection_graphs_d21_2026_10_16[].
See xref:reference.adoc#d33-three-collection-edges[].
See xref:internals.adoc#_query_graph_sql_loading_d14_2026_10_15[].

== Find entity graphs

[source,java]
----
var graph = em.createEntityGraph(Order.class);
graph.addSubgraph("customer").addAttributeNodes("address");
var order = em.find(Order.class, id, Map.of("jakarta.persistence.loadgraph", graph));
// The 3.2 typed overload applies the graph as a fetch graph:
var sameOrder = em.find(graph, id);
----

Eligible non-locking cache misses read direct/nested to-ones with the root through
LEFT joins (D15, 2026-10-16), including mapped composite root keys and converted
secondary-table state. LOAD adds mapped eager to-ones; FETCH may overfetch omitted
eager state. Managed/cache hits are not unnecessarily reread; graph state is completed
without overwriting dirty entities. Unloaded references hydrate in place.
Find never auto-flushes like a query. Mutable graphs are reread per call. If both hints
are supplied, find retains its existing merged plan, unlike query FETCH precedence.
Plain/locking finds, unsupported types/paths and collections retain complete ordinary
loading. Existing cache/lock/timeout/refresh contracts are unchanged.

== Bounded lazy reads

First access batches pending compatible lazy collections or to-one references in the
same persistence context. The default group size is 16. For a different factory-wide
bound, set:

[source,xml]
----
<property name="io.vidocq.noether.jpa.fetch.batch-size" value="32"/>
----

Values must be integers from 1 to 256; 1 disables grouping. Composite collection-owner
keys also respect a 512-key-parameter budget. This is separate from JDBC write batching.
Entity collections can require one collection-row statement plus several bounded
full-state target statements. They do not issue one `find` per element.
Lists, duplicate bags and maps preserve persisted null basic values, and empty owners
remain empty. To-one references hydrate in place; reading their identifier needs no SQL.

The optimization is bounded to single-table/non-polymorphic mappings and eligible D10
references. Complex mappings keep complete ordinary loading, not partial collections.
The current transaction connection is reused; pending writes are not auto-flushed.
Detached/cleared/closed contexts still reject unloaded access. For exact eligibility and
cache behavior, see xref:reference.adoc#_lazy_read_batching[].
